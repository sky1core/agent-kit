# 증거와 경계 감사

명세의 입력·표현 경계, 상태·자원 계약, 하네스 기반 증명, 차등 검사·기대 실패 게이트, 증명 결과 재사용을 다룰 때 읽는다. 해당 작업에 필요한 항목만 적용한다.

## 현재 입력에 대한 성공 증거

- 본문뿐 아니라 실제 선택된 소스·상수·표·helper·타입·명세·검증용 overlay·신뢰 계약·생성 입력과 도구 버전·옵션을 식별한다. 고정된 revision만으로 미커밋 변경이나 외부 입력까지 식별됐다고 간주하지 않는다.
- 도구가 실제 검사한 대상·명제, 실행의 종료 상태·속성별 결과·경고를 위 입력과 연결한다. proof artifact를 검사하는 방식이면 그 artifact에 대한 checker의 성공까지 확인한다. 작성자의 완료 선언이나 수동으로 고친 결과 파일로 대체하지 않는다.
- digest는 입력 식별 수단이지 증명 자체가 아니다. 관련 의존 입력이 누락됐거나 현재 입력에 대응하는 성공 결과가 없으면 미검증이다. 변경되지 않은 의무의 유효한 결과는 재사용하고 영향 범위만 다시 검증한다.
- 다른 도구나 검사에 맡긴 의무도 정확한 명제·전제·원본 대응과 결과를 확인한다. 등록 목록의 존재, 빈 게이트의 성공, 담당 문서에 대한 링크만으로 해소하지 않는다. 기존 도구 출력·캐시·짧은 의무 목록으로 충분하면 별도 관리 체계를 만들지 않는다.

## 값·표현·실행 조건

- 수학적 값, 저장 표현, 유효 상태, 부가 메타정보의 불변식을 분리한다. zero·부호·경계 exponent·표현 전환·중간 산술 범위의 작은 반례로 명세 오류를 먼저 찾되, 그 검사 자체를 증명으로 세지 않는다.
- 입력 제한이나 충분한 예산·미취소·비앨리어싱 전제를 추가했다면 실제 계약과 caller에서의 성립을 확인한다. 보장하지 못한 조건은 조건부 정리에 남기며, 원래 목표 영역의 반례를 없앴다고 하지 않는다.
- 수학적 크기 조건과 특정 저장 방식의 조건을 혼동하지 않는다. 절댓값이나 범위식을 코드로 계산할 때도 기계 정수의 overflow 가능성을 확인한다.
- 값·진단·상태·과금·한도 판정 중 무엇을 같게 요구하고 무엇이 승인된 차이인지 명시한다. 관찰할 계약 필드와 허용 차이는 결과를 보기 전에 정하며, 실패를 피하려고 분류를 바꾸지 않는다.

## 예약·변경·실패의 순서

- 최종 정산값과 실행 중 필요한 최대 자원을 구별한다. 최종 사용량이 0이어도 중간 예약이 필요할 수 있다. 관련 자원의 예약·누적 청구·정산과 실패 지점을 확인한다.
- 관련 경계의 직전·경계·직후에서 실패·취소가 발생할 때 반환값·오류·진단·출력 상태를 검사하거나 증명한다. 실패 후 미완성 scratch·중간 결과를 후속 연산이 소비하지 않는지 실제 caller까지 연결한다. 상태 보존·정산·부분 변경은 해당 계약에 따라 판단한다.
- 준비·캐시·scratch 등 재사용하는 상태를 비교 조건에 포함한다. 다른 요율이 승인됐으면 각 경로의 요율·예약·실패 계약을 검증한다. 요구되지 않은 동일 내부 trace를 강제하지 않는다.
- 자원 오류가 원래 진단을 가리거나 평가 순서가 바뀌는 경우도 공개 동작의 차이다. 원인이 비용 차이라는 설명만으로 허용하지 않는다.

## 차등 검사와 기대 실패 게이트

- 비교하는 두 경로가 실제로 실행되는지 확인한다. 같은 helper를 두 번 호출하는 것은 두 알고리즘의 비교가 아니다. 독립적인 값 oracle, 경로 간 동치, 관계식 검사는 각각 무엇을 확인하는지 구별한다.
- 복제한 평가 helper는 실제 공개 진입점의 값·오류·진단·상태와 대응시킨다. 관찰 레코드에서 계약 필드나 한도 카운터를 빠뜨려 동치로 판정하지 않는다.
- 기대 실패는 실행할 대상 집합·입력·예상 불일치 속성과 나머지 정상 조건을 고정한다. 누락·skip·다른 assertion·panic·timeout·빌드 오류를 예정된 속성 실패로 인정하지 않는다. panic 자체가 재현 대상이면 그 사건을 구체적으로 구별한다.
- 기대 실패 게이트의 성공은 알려진 결함의 정확한 재현이다. 등록 복구, 반례 재현, 수정 후 계약 충족을 구분한다. 알려진 반례를 제외하거나 관찰 필드를 무시해 정상 캠페인이 통과했다고 하지 않는다. 예상 실패가 사라지면 결함 수정 여부를 확인하고 해당 기대를 갱신한다.
- 하네스의 crash 부재 증명은 그 하네스가 실제로 호출·검사한 명제만 보장한다. 목표 속성을 확인하는 assertion을 제거·약화하거나 조기 반환으로 피한 결과를 제품 정합성으로 세지 않는다.

## 참고 자료

[Anthropic: LLMs are making formal software verification feasible at a much larger scale](https://www.anthropic.com/research/formal-verification)의 「Turning tests into proofs」, 「Limitations」, 각주 6을 참고한다.

- 특정 실행 모델·입력 범위·진입점의 명제를 checker가 확인한 사례다. crash 부재 보장을 라이브러리 전체의 기능 정합성이나 다른 실행 환경의 보장으로 확대하지 않는다.
- 증명 생성 에이전트와 증명 검사기를 구별한다. 검사 통과와 별개로 명제·언어 및 환경의 의미 모델·신뢰 기반이 제품 요구와 맞는지 확인한다.
- 프로그램을 사소하게 crash가 나지 않도록 바꾸는 편법도 명제를 통과시킬 수 있다. 제품 수정 시 원래 요구와 동작 변화를 대조하고, 기능 제거·입력 거부로 증명 성공을 만들지 않는다.

위 각 절의 쟁점을 더 확인할 때 다음 자료를 참고한다.
