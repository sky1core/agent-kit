# 형식 증명 원칙

**명시한 입력 범위에서 실제 제품 코드가 계약을 만족하는지 증명한다. 증명하지 못한 속성·입력·경로는 미증명으로 구분한다.**

프로젝트 전체를 무조건 증명 대상으로 확대하지 않는다. 사용자가 정한 목표 안에서 효과와 실현 가능성이 높은 범위를 선정하고, 부분 완료와 전체 목표 달성을 구분한다. 검증하기 어렵다는 이유로 요구를 낮추거나 실제 구현을 가정으로 바꿔 통과시키지 않는다.

**증명 대상은 실제 제품 코드다. 증명용으로 실행 코드를 바꾼 별도 구현·변환 사본으로 대체하지 않는다.** 수작업·스크립트·자동 생성 여부나 도구 제약·검증 비용은 예외가 아니다.

## 1. 무엇을 증명할지 정한다

대상 코드와 계약을 읽고 아래 항목을 짧게 정한다. 기존 문서가 있으면 중복 문서를 만들지 않는다.

- **대상과 입력:** 함수·호출 경로, 유효·무효 입력, 폭·길이·부호·표현·공유 상태·자원·환경의 범위.
- **명제:** 올바른 결과와 오류 조건, 보존할 상태·부수효과, 필요한 안전성·종료·동시성 속성.
- **경계:** 증명할 자체 코드, 신뢰하기로 한 검증기·언어 의미 모델·컴파일러·라이브러리·외부 환경, 남길 의무.
- **비용:** 대표 난점, 짧은 적용 실험, 중단·방법 전환 기준, 완료 판정.

명세는 요구에서 도출한다. 구현을 맞다고 전제하고 그것에 맞춰 명세를 쓰지 않는다. 구현과 명세가 충돌하면 요구와 대조해 어느 쪽이 틀렸는지 판단한다. 명세 오류는 원래 요구와 변경 승인 경계를 확인해 바로잡는다. 실패를 없애기 위한 입력 제한·사후조건 약화·오류 허용은 하지 않는다.

요구나 정답이 미정이면 현재 동작을 정답으로 고정하지 않는다. 결정이 필요한 항목과 현재 관찰을 분리해 남긴다.

성공한 경우의 값만 제약하면 항상 오류를 반환하는 구현도 통과할 수 있다. 계약이 정한 성공·실패의 조건을 양방향으로 표현하고, 값·정밀도·반올림·오류 종류·상태 변화 중 필요한 항목을 빠뜨리지 않는다.

수학적 값과 구현 표현을 구분한다. 값이 같아도 저장 방식·유효성·부가 메타정보는 다를 수 있다. 크기·부호·zero 조건과 표현 불변식을 별도로 정의하고, 작은 결과에서 입력 표현이나 실행 경로를 역추론하지 않는다.

동치의 항목을 먼저 고정한다. 값, 오류·진단, 상태는 서로 다른 명제다. 자원 계량 계약이 있으면 과금과 한도에서의 실행 허용 여부도 구분한다. 요율이 다르면 같은 예산의 성공 여부도 달라질 수 있으므로 요구한 동치와 허용 요율·실패 계약이 양립하는지 확인한다. 승인된 요율 차이를 다른 공개 동작 차이의 면책 근거로 삼지 않는다.

## 2. 실제 코드에 맞는 방법을 고른다

Rust는 [Rust 참조](references/rust.md), Go는 [Go 참조](references/go.md)를 읽는다. 다른 언어도 아래 증거 구분과 공통 원칙을 적용한다.

검증 도구의 번역·추출은 실제 제품 소스를 입력으로 하고, 문서화된 언어 의미·지원 범위·신뢰 기반을 확인한 경우에 사용한다. 제품과 별개로 실행 코드를 재작성·변환해 입력하거나 생성된 실행 의미를 수정하지 않는다. 변환기에 대한 신뢰 선언으로 이 조건을 대체하지 않는다.

| 증거 | 주장할 수 있는 범위 |
|---|---|
| 서술 논증·수동 수학 모형 | 논증 또는 모형의 명제. 실제 코드와의 대응은 별도 의무다. |
| 실제 제품 소스를 입력으로 하는 기계 증명(도구의 번역·추출 포함) | 검증한 빌드·입력·명제와 도구의 번역·언어 의미·외부 모델을 신뢰한 범위의 코드. 변환기 자체·호출부·외부 구현·생성 기계어까지 검증됐다고 확대하지 않는다. |
| 테스트·차등 비교·변이 검사 | 실행한 사례나 검사의 결함 탐지 근거. 그 자체로 모든 입력에 대한 정리를 대신하지 않는다. |

소스 revision, 대상 architecture, 조건부 컴파일·feature·build tag, 정수 폭, 외부 모델을 확인한다. ghost·annotation은 실행 코드를 대체하거나 바꾸지 않아야 하며, 이를 제외한 실행 코드와 실제 호출 대상이 제품과 같은지 확인한다. 해시·수동 대조·유한 테스트는 입력 일치나 차이 탐지의 보조 근거이며, 실행 코드가 달라진 사본을 원본 증명으로 인정하는 근거가 아니다.

수학 정수의 항등식은 기계 정수 구현의 정확성을 자동으로 보장하지 않는다. overflow·wrap·cast·shift·나눗셈·나머지·배열 경계와 계약의 대응을 보인다. 부동소수점은 해당 반올림·특수값·연산 의미를 따로 다룬다.

## 3. 작은 범위에서 시작해 합성한다

실제 대상의 작은 함수와 대표 난점으로 도구 지원·필요 가정·풀이 시간·작성 비용을 확인한다. 쉬운 예제 하나의 성공만으로 전체 적용 가능성을 단정하지 않는다. 도구의 버전·실제 옵션·지원 기능을 확인한 뒤 실행한다.

- 작은 대상 하나에서 실제 코드·명세·검증기 결과의 연결을 먼저 끝낸다. 호출 경로의 상태·자원 보장을 주장하면 실제 호출부와 실패 후 사용 경로도 포함한다. 검증 단위가 없는 게이트 통과를 제품 코드의 증명으로 인정하지 않는다.
- 보조정리와 함수 계약을 증명해 상위 경로에서 재사용한다. 추가한 전제조건·접근 권한은 실제 호출자나 입력 경계가 보장함을 증명한다. 반례를 전제 밖으로 옮기기만 하지 않는다. 연결하지 못한 전제는 조건부 정리의 한계로 남긴다.
- 다른 검사로 넘긴 의무는 실제 대상 명제와 성공 결과까지 확인한다. 문서끼리 서로 담당한다고 가리키는 것으로 의무가 해소되지는 않는다.
- 입력을 나눴으면 각 부분의 결과와 합집합이 원래 목표 영역을 덮는지 확인한다. 길이·폭·generic 인스턴스 일부를 전체로 확대하지 않는다.
- 루프 불변식의 초기 성립·보존·종료 시 결론을 연결한다. 종료가 요구되면 감소량뿐 아니라 호출 관계와 필요한 환경 가정까지 확인한다.
- 증명이 막히면 실제 코드 오류, 명세 오류, 부족한 불변식·lemma, 도구 제약, 계산 비용을 구분한다. 검증 실패만으로 버그나 명제의 거짓을 단정하지 않는다.

같은 실패에 시간 제한만 늘리지 않는다. 불필요한 전개를 줄이고, 증명된 계약·보조정리·완전한 도메인 분할·적합한 산술 이론이나 다른 도구를 검토한다. 원본 미지원이면 사본 변환으로 우회하지 말고, 원본의 해당 영역을 처리할 방법을 다시 선택한다. 방법 전환으로도 해결되지 않으면 정확히 미증명으로 남긴다. 목표 범위를 충족하지 못했으면 전체 완료로 보고하지 않는다.

자원 제한·취소·가변 상태가 있으면 최종 값뿐 아니라 중간 전이를 검증한다. 예약·청구·정산·변경 순서와 실패 시 보존할 상태를 확인하고, 미완성 결과를 다음 연산이 소비하지 않는지 확인한다. 최종 사용량만으로 실행에 필요한 최대 예약량이나 오류 우선순위를 판단하지 않는다. 계약 위반을 발견하면 증명 성공으로 덮지 않고 보고하며, 수정은 승인된 작업 범위에서 한다.

## 4. 잘못된 증명 주장을 판별한다

| 잘못된 처리 | 확인·교정할 내용 |
|---|---|
| 별도 구현·변환 사본의 증명을 원본 증명으로 보고함 | 사본의 성질은 원본의 정합성을 보장하지 않는다. 실제 제품 코드·명세·검증 결과가 연결된 경우에만 원본에 대한 증명으로 판정한다. |
| 미증명 구현과 결과가 같으니 정확하다고 함 | 동치와 정합성을 구분한다. 기준 구현도 계약을 만족하는지 증명하거나 독립적인 수학 명세에 연결한다. |
| 명세가 구현과 같은 표·상수·helper를 따라 결과를 정의함 | 같은 오류를 공유하면 증명이 통과할 수 있다. 공유 부분의 정확성도 독립적인 수학 정의·원래 계약에 연결해 증명한다. |
| 어려운 자체 함수를 스텁·가정·신뢰 선언으로 대체함 | 대체 대상의 같은 입력·부수효과 계약이 별도로 증명됐는지 확인한다. 없으면 그 함수에 의존하는 결론은 조건부이며 자체 코드 증명 완료로 세지 않는다. |
| 불편한 분기를 자르거나 특정 오류를 무시함 | 제거한 경로를 명시하고 실제 경로와의 관계를 확인한다. 빠른 경로만의 정리는 전체 함수의 정리가 아니다. |
| 검사하기 쉬운 입력만 남김 | 전제가 실제 계약인지 확인한다. 임의의 크기·값·상태 제한을 지원 영역 전체의 증명으로 보고하지 않는다. |
| 전제가 모순이거나 검증 지점에 도달하지 못함 | 전제의 만족 가능성과 필요한 경로의 도달성을 확인한다. 목표 결론을 전제에 넣는 순환 논증을 제거한다. |
| 약한 명세·빠진 사후조건으로 아무 구현이나 통과함 | 요구의 성공·실패·상태 조건과 대조한다. 계약을 위반하는 본문 제거·변경도 통과하면 해당 결과를 정합성 증거로 채택하지 않는다. 필요하면 중요한 결함을 넣어 관련 속성의 실패를 확인하되, 변이 몇 개의 거부를 명세 완전성의 증명으로 삼지 않는다. |
| 검증 개수·성공 문구·소스 키워드만 확인함 | 실제 검증된 함수·명제·입력·가정의 식별을 도구 출력과 대조한다. 누락·skip·미지원 경고와 검증 비활성 옵션을 확인한다. |
| 본문·manifest의 해시를 맞춰 재증명했다고 함 | 관련 의존 입력 전체와 도구 설정에 대응하는 실제 성공 실행 결과를 확인한다. 해시나 성공 표시를 수동 갱신한 것은 실행 증거가 아니다. |
| 증명되지 않은 보조정리·외부 계약을 숨김 | 직접·전이적 의존성을 확인한다. 허용한 신뢰 기반과 자체 코드의 미증명 의무를 구별한다. 다른 증명기로 넘긴 정리도 가정·타입·연산 의미가 일치하는지 확인한다. |
| 반환값이 맞으니 종료·동시성도 맞다고 함 | 부분정확성·종료·메모리 안전·race freedom·deadlock freedom·진행성 등 실제 증명한 속성만 주장한다. |
| 반례가 아직 없으니 증명됐다고 함 | timeout·unknown·미완료는 미증명이다. 제한 도메인의 완료 결과와도 구분한다. |

변이 검사는 분리된 임시 사본에서 필요한 결함에 한정한다. 문법 오류·빌드 실패·시간초과를 관련 명제의 실패와 혼동하지 않는다. 임시 변경을 원본에 섞지 않고, 이번 검사를 위해 만든 사본·산출물만 정리한다. 기존 증명·사용자 기록은 삭제하지 않는다.

기대 실패는 예정한 대상·입력·속성의 실패인지 확인한다. 단순 실패 상태를 통과로 뒤집거나 알려진 반례를 제외해 정상 검증으로 보고하지 않는다. 실제 경로 비교와 독립 정답 검증을 구별한다. 명세의 경계·자원 실패·하네스·차등 검사·검증 게이트를 다루거나 증명 결과를 재사용할 때는 [증거와 경계 감사](references/evidence-and-boundaries.md)를 읽는다.

외부 라이브러리와 컴파일러를 신뢰하는 정책은 허용할 수 있다. 그 정책이 자체 코드를 증명 없이 믿어도 된다는 뜻은 아니다. 외부 계약을 직접 작성했다면 원래 API의 조건·반환값·오류·부수효과와 일치하는지도 검토한다.

## 5. 필요한 검증만 하고 결과를 정확히 남긴다

증명 작성·유지 시간과 solver 실행 시간은 다른 비용이다. 기존 검증기의 출력과 간단한 의무 목록으로 충분한지 먼저 보고, 검증 도구 개발이 본래 목표를 대체하지 않게 한다.

- 작업 중에는 변경된 코드·명세·lemma와 영향을 받는 호출·의존 범위만 검증한다. 관련 테스트는 명세·코드의 연결이나 증명 밖의 구체적 실패를 확인할 때 사용한다.
- 선택한 영역의 최종 통합본에 필요한 전체 증명을 확인하고 유효한 결과는 재사용한다. 단순 문서 서술·리뷰 대기·세션 재개 때문에 전체 증명·테스트·벤치를 반복하지 않는다.
- 본문이 같아도 상수·표·helper·타입·명세·ghost·harness·신뢰 계약·도구·빌드 조건의 변경은 증거를 무효화할 수 있다. 현재 관련 입력에 대응하는 성공 기록이 없으면 stale 또는 미검증으로 남긴다. 유효한 캐시·기존 실행 기록을 활용하며 별도 관리 시스템을 무조건 만들지 않는다.
- 코드와 실행 조건이 바뀌지 않았다면 성능 벤치를 자동으로 돌리지 않는다. 증명된 내용과 같은 주장을 확인하려고 대규모 전수 검사를 무조건 덧붙이지 않는다.

보고에는 **대상·revision과 관련 입력 식별 / 정확한 입력·명제 / 신뢰 가정 / 도구·설정·실행 결과 / 남은 의무**를 남긴다. 적용 가능성만 조사했으면 실제 증명을 실행한 것처럼 쓰지 않는다. 반례는 원본 코드·입력·위반 속성으로 연결한다. 모형·내부 함수의 반례와 외부 입력으로 도달 가능한 제품 결함을 구분한다.

완료 판정은 선택한 범위의 요구·실제 코드·입력·가정·검증 결과가 맞물리는지로 한다. 통과 개수나 “증명 완료”라는 문구는 그 연결을 대신하지 못한다.
