# 최적화 원칙

정확성과 계약을 유지하면서 실제 작업의 총비용을 단순하고 일반적인 방법으로 줄인다. 벤치 행별 승패나 개선율을 목표로 삼지 않는다.

판단의 우선순위는 다음과 같다.

1. **필수 조건:** 정확성·계약·명시된 성능·메모리 한도를 지킨다. 다른 지표의 이득으로 위반을 상쇄하지 않는다.
2. **실제 목표와 총손익:** 같은 작업과 비교 가능한 자원 조건에서 목표 지표의 개선을 평가한다. 최적화 작업에 드는 시간과 복잡성·유지 비용도 후보 선정 때부터 반영한다.
3. **보조 지표:** 할당 횟수·명령 수·캐시 미스는 원인을 설명하는 수단이다. 처리량이 목표라면 할당 감소보다 실제 처리량을 우선한다. 메모리 절약이 목표이거나 한도가 있으면 그 조건을 우선한다.

사용자가 개선하려는 작업·지표·필수 조건을 먼저 확인하고 비교 기준을 정한다. 결과에 맞춰 유리한 지표나 입력만 골라 바꾸지 않는다.

## 1. 세 축으로 우선순위를 정한다

실제 작업과 입력 분포에서 후보마다 다음 세 축을 구분한다.

| 축 | 확인할 내용 |
| --- | --- |
| 경로 내부의 상대적 비중 | 바꾸려는 부분이 그 경로 비용의 얼마나 큰 몫인가? 90%짜리 병목을 두고 1%짜리 부분에 매달리지 않는다. |
| 경로 자체의 상대적 호출 빈도 | 실제 작업에서 그 경로가 다른 경로보다 얼마나 자주 실행되는가? 동일 연산의 입력값별 경로도 분리해 본다. |
| 경로 자체의 상대적 비용 | 그 경로의 호출 한 번이 다른 경로보다 얼마나 비싼가? 빈도만 높거나 호출당 비용만 크다는 이유로 우선하지 않는다. |

비교할 작업량을 고정했을 때 후보의 예상 절약량은 다음으로 추정한다.

```text
예상 절약량 = 호출 횟수 × 경로의 호출당 비용 × 개선 대상의 내부 비중 × 그 부분의 비용 감소율
```

이를 근거로 큰 병목부터 고른다. 경로 내부의 개선율만 보거나 세 축 중 하나만으로 순위를 정하지 않는다. 구현 뒤에는 예상치 대신 경로 전체의 전후 비용으로 검증한다.

```text
총 절약량 = Σ [경로별 호출 횟수 × (변경 전 호출당 비용 − 변경 후 호출당 비용)]
```

느려진 경로는 음수로 포함한다. 경로 전체의 변화량에 내부 비중을 다시 곱하지 않는다. 중첩된 호출의 inclusive 비용을 중복 합산하지 않으며, 호출 횟수 자체가 바뀌면 전후 각각의 횟수와 비용으로 총량을 계산한다. 이 합은 합산 가능한 작업 비용의 비교다. 병렬 실행의 지연시간은 임계 경로와 실제 전체 실행 시간으로 확인한다.

## 2. 비율보다 절대 비용의 손익을 본다

**회귀율만으로 최적화를 기각하지 않는다. 절대 ns 증감과 호출 빈도를 함께 계산한다.** ns는 시간의 예시 단위이며, 작은 절대 비용의 큰 비율 변화에 집착하지 않는다.

동일 연산에서 입력값에 따라 다음처럼 바뀌었다고 하자.

| 입력 경로 | 변경 전 | 변경 후 | 호출당 손익 |
| --- | ---: | ---: | ---: |
| A | 1ns | 4ns | 3ns 손실 |
| B | 100ns | 50ns | 50ns 절약 |

- 같은 호출 횟수라면 한 쌍의 비용은 101ns에서 54ns로 줄어 약 46.5% 개선이다. A가 4배가 됐다는 이유로 버리지 않는다.
- A와 B의 호출 횟수를 각각 `nA`, `nB`라 하면 총 절약량은 `50 × nB − 3 × nA` ns다. `nA / nB < 50 / 3`이면 이득, 같으면 손익분기, 크면 손실이다(`nB > 0`).
- “4배가 됨”과 “400% 증가”를 혼동하지 않는다. 1에서 4는 300% 증가지만, 채택 판단의 핵심은 3ns 손실과 50ns 절약의 가중 합이다.

호출 분포가 없으면 동일 빈도나 특정 입력의 우세를 사실로 가정하지 않는다. 알려진 사용 형태와 합리적인 분포별 손익, 손익분기점을 제시하고 확인된 범위에서 판단한다. 분포를 완벽히 알아야 모든 개선을 시작할 수 있다는 새 차단 조건도 만들지 않는다.

모든 벤치 행이 빨라야 한다는 기준을 임의로 추가하지 않는다. 다만 사용자가 정한 개별 경로의 상한·지연시간·메모리 한도 같은 필수 조건은 총이득을 이유로 무시하지 않는다. 전체적으로 작은 경로라도 명시된 한도를 위반하면 해결 대상이다.

## 3. 간단한 구조 개선부터 한다

1. 불필요한 계산·변환·복사·할당·왕복과 중복 작업을 없앤다. 불변식이 보장된 내부 경로에서 검증을 반복하지 않되, 입력 경계의 필요한 검증은 유지한다.
2. 알고리즘·자료구조·자료 표현·데이터 흐름을 실제 계약에 맞춘다. 좁은 값에 불필요한 넓은 연산을 하거나, 이미 확정된 정보를 매번 다시 해석하는 구조부터 살핀다.
3. 남은 중요한 병목에서 국소 튜닝을 검토한다. 큰 구조적 낭비를 두고 분기 순서·인라이닝·코드 배치의 작은 차이를 반복해서 쫓지 않는다.

특정 벤치 값·문자열 모양·길이에 맞춘 지름길로 일반적인 문제를 해결했다고 하지 않는다. 특수화가 필요하면 실제 입력 부류의 공통 성질에 근거하고, 해당 부류의 변형과 경계에서도 성립하는지 확인한다.

플랫폼·ABI·컴파일러·LLVM 버전에 따라 우연히 유리해진 기계어를 보편적 개선으로 취급하지 않는다. 저수준 튜닝은 필요한 적용 범위에서 이득과 유지 비용이 뒷받침될 때 채택한다. 정적 명령 수 감소만으로 실제 속도 개선을 단정하지 않는다.

**코드 복잡성도 비용이다.** 이득이 작거나 불확실하면 난해한 분기·중복 경로·많은 배경지식을 요구하는 땜질을 추가하지 않는다. 비슷한 효과라면 단순하고 직관적인 구현을 고른다. 중요한 사용처는 판단이 애매할 때의 우선순위 근거이지, 다른 입력을 심각하게 망가뜨리거나 특정 벤치에 과적합할 허가가 아니다.

## 4. 계약을 유지하고 효과를 검증한다

**테스트는 변경으로 발생할 수 있는 실패를 발견하기 위한 수단이다.** 실행 전에 무엇이 깨질 수 있고 어떤 검사로 확인할지 연결한다. 기준 구현이나 계약에 근거한 기대값·불변식으로 정합성을 확인한다. 비교 양쪽이 같은 구현·입력으로 귀결되는 검사는 정답 근거로 세지 않는다. 검사 횟수나 단계 수를 품질의 근거로 삼지 않는다.

검증은 다음 순서로 한다.

| 시점 | 실행 범위 |
| --- | --- |
| 코드 변경 없음 | 제품 테스트·벤치를 다시 돌리지 않는다. 설명 문서 수정은 diff와 내용의 정확성만 확인한다. |
| 코드 변경 후 작업 중 | 변경 경로에 필요한 테스트와 관련 벤치 사례 몇 개만 가볍게 돌려 정합성과 개선 방향을 판단한다. 매 수정마다 전체 검사를 돌리지 않는다. |
| 후보 탐색·채택·구현·리뷰 지적 처리가 끝난 최종 통합본 | 필요한 전체 테스트와 전체 벤치를 한 번 실행해 통합 결과를 확인한다. 각 후보나 개별 수정의 끝을 최종으로 취급하지 않는다. |

코드 외에도 의존성·빌드 설정·코드 생성 입력 등 실행 결과에 영향을 주는 변경이 있으면 그 영향 범위를 검사한다. 파일 확장자가 아니라 실행 영향으로 구분한다.

**후보 탐색 루프에 풀테스트·풀벤치를 넣지 않는다.** 작업 중에는 `후보 변경 → 관련 테스트·짧은 벤치 → 기각 또는 유지 → 다음 후보`로 진행한다. 후보 변경·교체·중간 커밋을 전체 검증의 이유로 삼거나, 기각할 후보의 전체 검증을 기다리지 않는다. 유지한 후보도 최종 통합본의 전체 검증을 통과하기 전에는 완료로 보고하지 않는다.

- **벤치는 후보 선별부터 한다.** 기존 하네스를 우선 활용하고, 부족하면 실제 변경 경로를 호출하는 관련 사례 몇 개로 작은 비교를 만든다. 짧은 측정으로 명백한 이득 없음·손실·복잡성 대비 낮은 가치를 확인하면 후보를 버린다. 유망하거나 측정 불확실성이 판단을 좌우할 때만 입력 분포·반복 횟수·플랫폼 등 필요한 축으로 확대한다. 작은 비교는 후보 선별 근거이며 최종 성능 보장을 대신하지 않는다.
- **검증 도구를 별도 제품으로 키우지 않는다.** 판단에 필요한 근거를 얻을 수 있으면 도구 확장을 멈춘다. 에이전트가 덧붙인 검증 도구 때문에 작업이 반복해서 막히면 제품 결함과 도구 결함을 구분하고, 도구의 필요성과 검사 범위를 먼저 재판단한다. 필수 보장은 유지하되 불필요하게 추가한 절차를 완료 조건으로 만들지 않는다.

- 값뿐 아니라 정밀도·반올림·오류·진단·평가 순서·부수 효과 등 관찰 가능한 계약을 보존한다. 지원 범위나 기대값을 줄여 얻은 속도를 최적화로 포장하지 않는다. 사용자가 계약 변경을 승인했다면 변경된 계약에 맞춰 구조를 설계하고, 폐기한 계약을 임의로 보존하느라 개선을 방해하지 않는다.
- 실제 제품 경로를 검증한다. 내부 helper나 벤치 전용 경로의 이득을 전체 제품의 이득으로 확대하지 않는다.
- 같은 입력·작업량·빌드 조건에서 기준본과 변경본을 비교한다. 주요 변수는 한 번에 하나씩 바꾸고 툴체인·플랫폼·조건·샘플 수를 기록한다.
- 규모에 따른 비용 증가나 경합을 개선하려는 경우에는 선별 단계부터 소수 지점으로 가설을 확인한다. 단일 입력의 결과를 일반화하지 않는다. 최종 검증에는 대표 분포와 경계·불리한 입력을 포함하고, 응답시간이 요구사항이면 평균뿐 아니라 지연 분포도 확인한다.
- 할당 횟수·바이트·시간당 할당량과 보유·최대 메모리를 구분해 영향을 받는 지표만 본다. 풀·캐시의 준비·유지·정리 비용을 빼놓지 말고 실제 재사용 횟수에서 총이득인지 확인한다. 단위가 다른 비용은 억지로 합치지 않는다.
- 작은 차이가 판정을 좌우하면 기준본끼리의 반복 측정(A/A)이나 교차 측정으로 잡음과 코드 배치 효과를 구분한다. 잡음 안의 차이를 개선 또는 회귀로 확정하지 않는다.
- 채택할 최종 통합본에서 영향 경로와 실제 사용 흐름의 총효과를 확인한다. 통과한 검증은 재사용한다. 수정 뒤에는 결과가 무효화된 영향 범위만 다시 확인하고, 전체 결과가 무효화되거나 명시된 필수 절차가 요구할 때만 전체 검사를 다시 한다. 문구 수정·리뷰 대기·재개를 전체 검사 재실행의 이유로 삼지 않는다.

## 5. 손익을 판단하고 일단락한다

**최적화 작업 자체의 시간도 별도의 비용이다.** 제품의 실행 비용과, 그 개선을 얻기 위한 조사·구현·벤치 준비·측정·리뷰·재작업·대기 시간을 구분한다. 사용자 확인에 드는 시간, 공개 지연과 다른 중요한 일을 미루는 기회비용도 포함한다. 둘 다 시간 단위라고 CPU 시간 절약과 개발 소요 시간을 그대로 빼서 손익을 계산하지 않는다.

후보를 고를 때 예상 효과·적용 빈도·혜택이 지속될 기간과 함께 구현 난이도·남은 작업 시간·성공 가능성을 평가한다. 실행 시 조금 더 빠른 안이더라도 며칠의 추가 작업과 복잡성을 요구한다면, 짧은 시간에 확실한 큰 개선을 얻는 안을 우선할 수 있다. 작은 실험으로 더 조사할 가치부터 판단하고, 후보의 가치보다 큰 측정·검증 체계를 먼저 만들지 않는다.

**가능성 없는 후보는 빠르게 버리고 다른 최적화 방법을 찾는다.** 작은 실험에서 기대한 병목을 줄이지 못하거나, 필요한 개선 규모에 턱없이 못 미치거나, 복잡성에 비해 이득이 명백히 작으면 그 후보를 기각한다. 정밀 벤치·전체 검증·추가 미세 튜닝으로 억지로 살리지 않는다. 단순한 측정 오류인지 확인할 필요가 있다면 그 확인만 짧게 하고, 새 근거 없이 같은 방향을 반복하지 않는다.

기각한 이유를 짧게 남기고, 같은 목표를 달성할 다른 알고리즘·자료구조·데이터 흐름을 검토해 다음 유망 후보를 작은 실험으로 확인한다. 후보를 버리는 것은 최적화 목표나 요구사항을 포기하는 것이 아니다.

이미 쓴 시간이 아까워서 계속하지 않는다. 계속 여부는 **앞으로 얻을 추가 이득과 앞으로 더 들일 비용**으로 판단한다. 반복 실험이 결론을 바꾸지 못하면 해당 후보를 중단하고 더 가치 있는 방법으로 전환한다. 이를 빌미로 정확성이나 사용자의 필수 요구를 포기하지 않는다.

개선과 회귀가 함께 있으면 호출 분포로 가중한 총손익, 필요한 사용처, 코드 복잡성, 필수 조건을 함께 평가해 추천안을 정한다. 원인을 모르는 큰 회귀는 조사하되, 모든 행을 녹색으로 맞추기 위한 끝없는 미세 조정으로 바꾸지 않는다. 특정 플랫폼의 이득을 전체 플랫폼의 이득으로 보고하지 않는다.

명확하고 보편적인 개선을 먼저 마무리한다. 추가 기대 이득이 복잡성·측정·유지보수 비용보다 작거나 잡음 수준이면 해당 튜닝을 멈춘다. 이 판단으로 사용자 요구를 임의로 낮추거나 미충족 작업을 완료로 선언하지 않는다.

- **측정과 총손익:** 조건, 전후 절대 비용, 호출 분포, 전체 이득과 손실. 미확인 분포는 손익분기점과 한계.
