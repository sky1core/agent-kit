# 문서·주석 원칙

> 기본값은 남기지 않는 것이다. 남기는 쪽이 예외이고 근거가 필요하다.

도구가 읽는 주석은 주석이 아니라 코드다 — shebang, pragma·디렉티브(`# noqa`,
`eslint-disable`, `@ts-expect-error`, `//go:build` 등), 라이선스 헤더, 프로젝트의
문서 빌드·lint·런타임이 실제로 소비·강제하는 docstring(OpenAPI description,
CLI `--help`, doctest 등). 이 원칙의 대상이 아니며 정리에서 건드리지 않는다.
다른 코드와 같이, 내용이 거짓이 되거나 더 이상 맞지 않게 되면 그 변경에서 함께
고친다.

## 왜 최소로 남기나

주석과 문서는 대개 실행 경로에서 검증되지 않아 검증 압력이 약하다. 두 가지 방식으로
유지보수를 망가뜨린다.

- **Drift** — 코드를 고칠 때 사본을 전부 찾아 고치지 않으면 낡은 서술이 남는다.
  다음 에이전트는 그것을 지시로 읽고, 코드와 충돌하는 지침 사이를 오가며 고쳤다
  되돌렸다를 반복한다.
- **희석** — 주석이 전부 정확해도 양이 많으면 진짜 중요한 제약이 장식들 사이에
  묻힌다. 안전 불변식 하나를 살리려면 그 주위의 무의미한 주석을 지워야 한다.

## 남기지 않는다

- 바로 아래 코드를 자연어로 되풀이하는 주석
- 프로젝트 스펙·설계 문서의 **섹션 번호를 가리키는 주석**. 문서가 개정되면 전부 거짓이 되고,
  그 문서가 저장소에 없으면 따라갈 수조차 없다
- 변경 이력과 작업 서사("기존엔 X였으나 이제 Y") — git이 담당한다
- 판단 근거, 검토 과정, 개인 메모, 다음 작업 계획
- 자명한 함수·필드에 의무적으로 붙이는 docstring
- 공개 문서에 들어가는 내부 운영 맥락과 유지보수자 결정 이력

## 남기는 경우

주석은 둘 중 하나일 때만 남긴다.

- 사용자가 남기라고 지시했을 때
- 같은 자리에서 잘못된 수정이 **실제로 반복된 것이 확인**됐을 때

**예방적으로 붙이지 마라.** "앞으로 누가 여기를 잘못 고칠 것 같다"는 에이전트 본인의
예상일 뿐 확인된 적이 없다. 그 예상으로 붙인 주석이 쌓여서 진짜 중요한 것을 덮는다.

남길 때 주석은 설명이 아니라 **하지 말아야 할 행동**을 적는다. "X는 이렇게 동작한다"가
아니라 "X를 Y로 바꾸지 마라 — Z 때문에 깨진다".

## 주석보다 강한 수단을 먼저 쓴다

주석은 검증되지 않는다. 같은 내용을 강제할 수 있으면 그쪽을 쓴다.

1. **이름** — 함수·변수 이름이 하는 일과 일치하면 설명이 필요 없다
2. **타입·스키마** — 허용되는 값을 타입으로 좁힌다
3. **런타임 검증·assert** — 불변식을 코드가 강제한다
4. **테스트** — 지켜져야 할 행동을 실행 가능한 형태로 고정한다

남기기로 판정한 경우에도 주석은 위 넷으로 표현할 수 없을 때의 마지막 수단이다.

## 삭제 판정

기존 주석을 정리할 때 항목마다 묻는다.

- 근처 코드가 바뀌면 이 주석이 거짓이 되나 → 삭제하거나, 코드로 강제할 후보로
  보고한다
- 이 주석을 지우면 무엇을 잃나. 답이 안 나오면 삭제한다
- 이 주석이 없어도 코드를 읽고 같은 결론에 도달하나 → 삭제한다

정리는 주석만 바꾼다. 코드 토큰, 식별자, 문자열 리터럴은 건드리지 않는다. 삭제
목록을 먼저 제시하고 승인을 받은 뒤 적용한다.

적용 후 빌드·lint·테스트로 파일이 여전히 유효한지 확인한다.

정리 작업이 아니어도, 자신의 코드 변경으로 거짓이 된 인접 주석은 그 변경에서 함께
지우거나 고친다.

## 문서

- 지시받지 않은 문서를 새로 만들지 않는다. 빌드·CI가 강제하는 문서 파일은 지시로
  본다.
- 커밋할 문서와 임시 노트를 분리한다. 작업 노트와 분석 기록은 커밋하지 않는다.
- 새 문서를 만들기 전에 기존 문서에 들어갈 자리가 있는지 본다. 파일이 늘면 관리해야
  할 진실 후보가 늘어난다.
- 분량은 과제에 맞춘다. 채우기용 섹션, 중복 요약, 보일러플레이트로 길이를 늘리지
  않는다.
- 문서 파일을 삭제할 때는 목록을 먼저 제시하고 승인을 받은 뒤 적용한다.
- 스펙 문서에는 계약만 남긴다 — 불변식, 경계, 실패 시 동작. 구현 세부, 작업 경과,
  결정 서사를 스펙에 쓰지 마라. 스펙이 구현을 따라 매번 바뀌기 시작하면 계약이
  아니라 일기장이 된 것이다.
